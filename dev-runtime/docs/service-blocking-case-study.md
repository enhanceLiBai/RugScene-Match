# 内网穿透场景下的服务阻塞定位与并发优化

## 项目背景

地毯场景图片匹配系统部署于 Windows 本机服务器，使用 FastAPI、Docker PostgreSQL/pgvector、OpenCLIP 和 DeepSeek 场景识别，通过 Cloudflare Quick Tunnel 为不超过 8 名客服提供外网测试访问。

业务包括图片匹配、图库浏览、历史结果查看与图片下载。本次优化重点是避免慢图片传输和慢模型调用影响其他用户使用。

## 故障现象

接入临时隧道后，外网出现“服务暂不可用”、结果图片空白，内网也出现请求超时。进程存在或首页偶尔返回 200，并不意味着完整业务正常。

最初曾怀疑公网扫描、防火墙、DeepSeek 故障和进程退出，但没有充分证据证明这些是根因。后续通过数据库活动、接口日志和并发实测定位到具体代码路径，未发现可用于确认公网攻击的证据。

## 问题一：图片响应占用数据库连接

### 定位证据

- PostgreSQL 中观察到 15 个连接处于 `idle in transaction`，最后执行的均为图库图片记录查询，等待应用继续操作或释放连接。
- SQLAlchemy 使用默认连接池配置，单进程最多可同时占用 15 个连接（5 个常驻连接加 10 个溢出连接）。
- 图片接口通过请求级 yield 依赖获得 Session，返回 FileResponse 后，会话直到响应传输结束才释放。
- 日志出现多条 `/api/images/...` 的 503 响应。

### 原因与影响

原图经外网传输较慢时，数据库查询虽已结束，连接仍被图片响应占用。多个图片请求耗尽连接池，历史和匹配请求等待连接，进一步占用工作线程，影响内外网共享的后端。

这属于服务资源生命周期问题，不能简单归因于 Cloudflare 故障。单凭连接状态也不足以证明发生了进程崩溃。

### 修复

图片接口使用局部数据库会话，仅在会话内提取路径、MIME 类型和文件名；关闭会话后再构造文件响应。保留文件路径范围检查，并增加图库图片懒加载。

## 问题二：同步匹配逻辑阻塞事件循环

### 定位证据

`async def` 匹配接口内执行了同步模型加载、推理、数据库访问和外部识别调用。早期只给向量编码和初次场景识别加线程卸载，遗漏了同步执行的 `review_conflicts()` 双图复核。

早期全流程单并发限制也使用户逐个等待外部 API，放大队尾延迟。锁或信号量本身不能把同步工作变成非阻塞工作。

### 修复

- 使用 Starlette `run_in_threadpool` 执行完整同步匹配流程，包括模型加载、编码、场景识别、双图复核、数据库读取和历史保存。
- 用信号量将同时执行的匹配限制为 8 个，外部识别允许跨请求并行。
- OpenCLIP 编码使用实例级锁串行执行，避免同一模型并发争抢 GPU；不将外部 API 等待纳入编码锁。
- 每个匹配在线程中创建并关闭独立数据库会话，避免请求间共享 Session。
- 增加隔离测试：让 8 个模拟复核同时等待，验证首页仍可响应；释放后验证全部匹配完成及独立历史写入路径。

## 问题三：结果卡片直接下载大原图

匹配接口成功并不代表结果图片已经下载完成。两张实际结果原图分别约 4.6 MB、6.5 MB，外网加载容易产生卡片已出现但图片空白的感受。

增加 `?preview=1` 图片预览：最长边 1200 像素、JPEG 质量 88，最近 32 张预览在进程内缓存，浏览器缓存一小时。卡片加载预览，下载按钮仍获取原始文件。

实测两张预览分别为 197,813 和 185,177 字节，合计由约 11.15 MB 降为 0.383 MB，传输体积减少约 96.6%。原图保持不变。接口测试覆盖预览格式、尺寸上限及下载原图行为。

## 测试与结果

以下是 2026-09-15 的有限轮次测试结果，不是长期 SLA、生产容量承诺或不同终端网络的全面测试。外网请求由服务器通过公开隧道域名发起，模拟 8 个并发客户端；未使用 8 台真实外网设备。

| 场景 | 优化前观察 | 优化后观察 |
| --- | --- | --- |
| 本机 8 并发首页 | 平均约 56.6 秒 | 约 0.19 秒，全部 200 |
| 本机 8 并发历史列表 | 全部失败或超时 | 约 0.15 秒，全部 200 |
| 外网 8 并发浏览 | 首页及历史列表共 16 个请求全部超时 | 首页、历史、详情和图片共 40 个请求全部 200，单请求约 0.69～2.24 秒 |
| 外网同图 8 并发匹配 | 4 次有结果、3 次空结果或识别异常提示、1 次约 182 秒客户端超时 | 8 次均返回 200 且各有 1 个结果；7 次约 23.67～24.92 秒，1 次 54.29 秒，平均 28.09 秒 |
| 匹配期间本机历史查询 | 多次超过 5 秒超时 | 采样均为 200，约 0.02～0.06 秒 |

匹配测试使用同一客户照片，正常调用模型并生成历史记录。最慢请求有一张候选复核未完成的提示；HTTP 200 不代表每次外部复核全部成功。前后测试间发生服务重启，模型缓存状态、网络和外部 API 响应并未严格控制，因此不能把全部耗时差异归因于单一修改。

## 剩余限制

- 单张图片仍要初次识别和最多 3 次逐张复核，线程卸载不等于减少单次外部调用耗时。
- 未采集完整的分阶段耗时，尚不能定量区分模型冷启动、GPU 编码、DeepSeek 服务端及网络等待。
- 尚未完成不同图片、长期运行、多人匹配同时批量导入等组合验证。
- 8 个匹配的并发限制适用于当前单进程；Quick Tunnel 不提供稳定时延保证。
- 未建设持久化匹配任务队列；请求超时不等于后台工作自动停止。

## 面试讲解顺序

1. 现象：外网图片加载后，内网也超时；先区分进程存活和业务可用。
2. 证据：数据库连接等待状态、图片 503、同步调用位置及并发期间轻量请求超时。
3. 原因：数据库连接占用跨越图片传输，同步计算和外部调用占据事件循环。
4. 取舍：面向 8 人内部业务，优先缩短资源持有时间和线程卸载，不引入分布式任务系统。
5. 验证：分别测浏览与真实匹配，并探测匹配期间轻量接口，避免只用首页 200 宣称修复。
6. 边界：解释单图复核延迟、单轮测试限制和下一步分阶段耗时观测。
