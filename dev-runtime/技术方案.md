# 地毯买家秀智能匹配助手：技术方案

> 状态：方案 v0.1  
> 更新：2026-08-28  
> 定位：内部客服辅助决策系统，不在早期承诺全自动选款。

## 1. 目标与范围

客服收到客户家居图后，系统在优质买家秀中找到最接近的场景，提供可参考的实拍案例、可销售的地毯 SKU（仅限已确认关联的图片）及可复制的话术。

首期规模为 1 万+ 张买家秀、8 人以内并发，后续持续增量更新。目标是将客服翻找图片和组织话术的时间缩短到数秒，而不是替代客服判断。

### 首期不做

- 不将未确认来源的图片自动推荐为某个具体 SKU。
- 不让模型猜测价格、规格、材质、库存或促销信息。
- 不以一次性人工标注全部 1 万张图片作为上线前置条件。

## 2. 核心原则

1. **图像向量负责“像不像”**：比较整体空间、色调、构图和视觉风格。
2. **结构化标签负责“适不适合”**：按房间、风格、颜色等进行筛选与重排。
3. **商品真实数据负责“能不能卖”**：SKU、规格、价格、库存只能来自商品系统或人工确认。
4. **生成式 AI 只做受约束的事情**：输出固定 JSON 标签和基于事实字段的话术，不自由编造商品事实。
5. **人工反馈是训练数据**：客服确认、改正或否决的推荐，会反哺图库和排序规则。

## 3. 分层图库设计

| 图库层级 | 数据来源 | 可做什么 | 不可做什么 |
|---|---|---|---|
| 场景参考库 | 全量历史照片，经 AI 自动分析 | 找相似装修案例、展示搭配方向 | 直接推荐具体 SKU |
| 可推荐库 | 已人工确认图片与 SKU 的关联 | 推荐商品、生成客服话术 | 跳过库存/商品规则 |
| 待审核库 | AI 低置信度、同图多地毯、来源不明 | 排入审核队列 | 参与商品推荐 |

## 4. 建库策略

### 4.1 首批人工确认范围

先建立 500–2,000 张高质量买家秀的可推荐库，不必标完全部历史照片。优先选择：

- 主推、高销量或库存稳定的 SKU；
- 客厅、卧室、玄关等主要空间；
- 奶油风、原木风、现代简约等主要风格与主流色系；
- 地毯主体清晰、拍摄质量高、效果有代表性的图片。

每张首批图片至少确认：`图片 ID`、`SKU`、`商品名称`、`可售规格`、`颜色`、`库存状态`。

### 4.2 AI 自动补充字段

多模态模型为全量图片生成受约束的 JSON 标签。建议字段：

```json
{
  "room": "客厅",
  "style": ["奶油风", "现代简约"],
  "space_size": "中等",
  "floor_color": "浅木色",
  "main_colors": ["米白", "浅咖"],
  "carpet_color": "米白",
  "carpet_shape": "长方形",
  "carpet_texture": ["短绒", "简约纹理"],
  "matching_highlights": ["低饱和配色与浅木地板协调"],
  "confidence": 0.83
}
```

字段取值必须受预设枚举控制；不能识别时输出 `unknown`，不能猜测。低置信度或检测到多张地毯的记录进入待审核库。

### 4.3 上线后的自然补标

客服每次使用推荐时都可做三种反馈：确认 SKU、改为其他 SKU、标记不合适。确认或更正的结果写回图库，使未关联 SKU 的场景图逐步转为可推荐图。这比集中标注全部 1 万张更省成本，也更贴近真实销售场景。

## 5. 技术架构

```text
图片导入 / 增量上传
  ├─ 图像质量与去重检查
  ├─ 多模态模型：图像向量 + 结构化标签
  └─ 写入对象存储、业务数据库、向量索引

客服上传客户家居图
  ├─ 生成查询图像向量
  ├─ 向量检索召回 Top 50 场景图
  ├─ 空间 / 风格 / 预算 / 库存等规则重排
  └─ 返回 Top 3–5：实拍图、SKU、推荐理由、话术
```

建议正式版使用：对象存储保存原图和缩略图；关系型数据库保存商品、标签、审核和操作记录；向量数据库保存图像向量。1 万至数十万图片可先选 PostgreSQL + pgvector，后续规模或检索要求提高时再迁移至专用向量库。

当前静态 MVP 用浏览器本地数据和轻量图像特征跑通流程，不是正式架构。

## 6. 匹配与话术规则

### 匹配顺序

1. 客户图按图像向量召回视觉接近的 Top 50。
2. 结合空间、风格、色调、户型/面积等标签重排。
3. 对可推荐库，再检查 SKU 是否在售、是否有合适规格、是否满足预算。
4. 输出 Top 3–5；低分或缺乏可售 SKU 时，明确提示客服人工选择，不强行推荐。

### 话术生成边界

话术由「已确认商品字段 + 场景标签 + 推荐理由」拼装或由模型润色。允许表达视觉搭配建议；不允许生成未验证的材质、价格、库存、优惠、尺寸承诺。

## 7. 实施阶段与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1：流程 MVP | 图库录入、客户图上传、基础匹配、话术、反馈 | 客服可独立完成一次推荐流程 |
| 2：真实数据建库 | 批量导入、自动标签、人工审核、首批 500–2,000 张 SKU 关联 | 可推荐库覆盖主推 SKU 与主要场景 |
| 3：语义检索 | 多模态图像向量、Top 50 召回、规则重排 | Top 3 推荐在抽样人工评审中有稳定命中率 |
| 4：业务闭环 | 商品库存/规格接入、反馈回写、运营看板 | 客服反馈可持续补齐 SKU 与标签 |
| 5：正式上线 | 多账号、权限、云端部署、监控与备份 | 8 人并发稳定使用，图片与日志可追溯 |

## 8. 指标

- Top 3 场景相似度人工命中率；
- 推荐被客服直接采用的比例；
- 客服改正 SKU 或标记不合适的比例；
- 单次推荐平均耗时；
- 可推荐库中 SKU 已确认图片的占比；
- 低置信度标签的人工修正率。

## 9. 风险与处理

| 风险 | 处理方式 |
|---|---|
| 历史图没有 SKU | 分为场景参考库与可推荐库；从首批人工标注和客服反馈逐步补齐 |
| 图片中有多张地毯/主体不清晰 | 模型标记低置信度，进入待审核，不直接推荐 |
| 模型编造商品信息 | SKU、价格、规格、库存只读业务系统字段；话术输出加事实校验 |
| 客户图隐私 | 明确保留期限、访问权限、是否允许传云端模型；必要时选择私有化模型 |
| 标签口径不统一 | 先定义可选空间、风格、色系枚举；运营审核时统一口径 |

## 10. 下一步决策

1. 确认可用买家秀来源、文件格式和图片总量。
2. 确认是否能从订单、文件名、聊天记录等渠道获得 SKU 关联线索。
3. 定义首批主推 SKU 和标注范围。
4. 明确客户/买家图片是否可传给云端模型处理。
5. 以小批真实数据完成一次建库试跑后，再确定正式模型与部署方式。
